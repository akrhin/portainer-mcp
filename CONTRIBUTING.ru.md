# Как участвовать

Спасибо, что нашли время. Здесь — что должно быть в изменении, чтобы его приняли.

## Требования

- Go 1.27 или новее (`go.mod` пинует `go 1.27.4`).
- Инстанс Portainer и менеджер Arcane для `arcane-mcp`, если изменение трогает поведение тулов. Интеграционные проверки идут против живого сервера; юнит-тестам он не нужен.
- Больше ничего: сборка, проверки и тесты — обычные команды `go` за Makefile.

## Сборка и ворота

```sh
make build        # go build -o portainer-mcp ./cmd/portainer-mcp
make build-arcane # go build -o arcane-mcp ./cmd/arcane-mcp
make check        # gofmt -l ., go vet ./..., go test ./...
```

`make check` — это ворота. Pull request, который их не проходит, не ревьюится.

Перед открытием pull request прогоните ещё:

```sh
go test -race ./...
bash scripts/docs-check.sh
```

Детектор гонок обязателен для всего, что трогает горутины, HTTP-транспорт, потоковый вывод или общие кэши. Ворота документации проверяют ссылки, языковой паритет, личные пути и факты, закреплённые в `docs/anchors.txt`.

## Порядок работы

1. Ветка от `main`. Одна ветка — одно логическое изменение.
2. Коммит в формате Conventional Commits: `feat:`, `fix:`, `docs:`, `test:`, `refactor:`, `chore:`. Необязательный scope помогает: `feat(catalog): ...`.
3. Pull request в `main`: опишите, что меняется для пользователя, а не какие файлы вы правили.

Держите дифф обозримым. Рефакторинг и изменение поведения в одном pull request — это два pull request.

## Что приложить к pull request

- Тест на новое или изменённое поведение. В проекте приняты табличные тесты; golden-тест держит каталог и список зарегистрированных тулов в согласии.
- Запись в [CHANGELOG.md](CHANGELOG.md) под заголовком `## [Unreleased]` в начале файла — создайте его, если его нет, — в разделе по типу изменения (`Added`, `Changed`, `Fixed`, `Removed`).
- Правку документации, если меняются поведение, ключи конфигурации, имена тулов или значения по умолчанию. Факт на странице обязан совпадать с кодом в том же pull request.
- Никаких секретов и личных путей. CI гоняет gitleaks; `.env`, `*.key` и `config.local.yaml` исключены из git и должны оставаться вне коммитов.
- Никаких внутренних хостов, IP-адресов и домашних каталогов в коде, тестах, фикстурах и документации. Репозиторий публичный.

## Стиль

Обычный Go, написанный так, как написана стандартная библиотека.

- Ошибки оборачиваются с контекстом: `fmt.Errorf("inspect container %s: %w", id, err)`. Исходную ошибку не терять.
- Не вводите интерфейс, пока нет второй реализации. Конкретного типа и функции достаточно.
- Никаких options-структур, обёрток и абстракций ради одного вызывающего.
- Каталог остаётся декларативным. Имена тулов, описания, аннотации и схемы живут в `api/`, а сгенерированный каталог их несёт; код читает их и не дублирует.
- Комментируйте причину, а не механику.

## Как добавить тул

Поверхность тулов — это данные. Не правьте `internal/catalog/generated.yaml` и не пишите обработчик: все операции исполняет один общий обработчик.

1. Добавьте или перенесите операцию в `api/toolsets.yaml` — карта тегов, переопределение `operation_toolsets`, переименование или запись в `extras`. У профиля Arcane тот же файл — `api/arcane-toolsets.yaml`.
2. Решите, входит ли операция в набор по умолчанию: `api/default-tools.yaml` (или `api/arcane-default-tools.yaml`).
3. Прогоните `make catalog`, затем `make catalog && git diff --exit-code internal/catalog/generated.yaml` — второй прогон не должен ничего менять.
4. Добавьте запись в CHANGELOG и обновите страницу наборов или конфигурации в том же pull request.

Ворота после этого: `make check`, `go test ./tools/cataloggen`, `bash scripts/docs-check.sh`. `ReadOnly` и `Exhaustive` меняют состав зарегистрированных тулов, поэтому новому тулу нужен случай в тесте регистрации.

Имена наборов, описания и `depends_on` живут в `internal/catalog/catalog.yaml` (`internal/catalog/arcane/catalog.yaml` для Arcane). Списков тулов в этом файле нет.
