# Бэкенд Arcane

Из этого репозитория собираются два MCP-сервера на одном генераторе каталога:
`portainer-mcp` говорит с Portainer, `arcane-mcp` — с менеджером
[Arcane](https://getarcane.app). Они делят обработчик, типы конфигурации и встроенный
каталог, а в MCP-клиенте включаются независимо.

Arcane 3.0.1 отвечает JSON под `/api` и авторизует по заголовку `X-API-Key`. Каталог
содержит 445 тулов в семнадцати наборах; 53 регистрируются по умолчанию, а
`--exhaustive` регистрирует все операции включённых наборов. Каждая из 444 операций
документа достижима тулом.

## Откуда берутся тулы Arcane

| Файл | Роль |
|---|---|
| `api/arcane-3.1.yaml` | Сконвертированный документ OpenAPI; его пишет `tools/specgen`, руками не правится |
| `api/arcane-toolsets.yaml` | Карта тегов в наборы, переопределения, пути с дедлайном, переименования и extra `arcane_raw` |
| `api/arcane-default-tools.yaml` | 53 тула, регистрируемых без `--exhaustive` |
| `tools/cataloggen -profile arcane` | Читает три файла выше и пишет `internal/catalog/arcane/generated.yaml` |
| `internal/catalog/arcane/catalog.yaml` | Имена наборов, описания и рёбра `depends_on` |
| `internal/catalog/arcane/generated.yaml` | Все тулы всех наборов; встроен в бинарь |

`catalog.LoadArcane()` сливает два документа так же, как каталог Portainer, поэтому
проверка — дубли имён, отсутствующие аннотации, неизвестные зависимости — одна и та же.
`make catalog` перестраивает оба каталога за один прогон.

| `volumes` | `core` | 26 | 3 |
| `networks` | `core` | 8 | 3 |
| `projects` | `core` | 46 | 6 |
| `backups` | — | 27 | 3 |
| `gitops` | `core` | 26 | 4 |
| `swarm` | `core` | 54 | 4 |
| `podman` | `core` | 26 | 2 |
| `security` | `core` | 42 | 4 |

| `uploads` | `core` | 4 | 0 |

| `auth` | `core` | 31 | 0 |

Всего 445 тулов, 53 в наборе по умолчанию. `backups` и `raw` стоят отдельно, остальным
нужен `core` — в нём вызовы окружений (агентов) и системы. Наборы `uploads`, `push` и
`auth` по умолчанию выключены: загрузка чанка, регистрация устройства APNs и церемония
MFA или OIDC управляются человеком или устройством, а не моделью, поэтому закрытый
набор открывается только по явному запросу клиента.

В `events` лежат `stream_client` и `wait_for_environment_changes`: обычный запрос на них
повис бы, поэтому ответ читается до дедлайна. У таких тулов есть аргумент `timeout_sec`
(целое, по умолчанию 10, от 1 до 60); ответ — то, что сервер успел прислать, с хвостом
`…[stream read stopped at timeout_sec: raise it to read longer]`. То же у
`stream_upgrade_progress`.

Если документ объявляет единственным телом запроса `application/octet-stream`
(например, `upload_chunk`), тело задаётся как `{"content": "текст"}` или
`{"base64": "..."}` и уходит байтами без изменений: файлу не нужно становиться
JSON-строкой из экранированных символов.

Тело, которое документ объявляет плоским объектом из скаляров, не оборачивается:
`settings_search` принимает `query`. Тело с вложенными объектами или свободными
ключами сохраняет обёртку `body` и передаётся как есть.

Arcane адресует ресурсы через агента: пути выглядят как
`/api/agents/{id}/containers/{containerId}`, где `id` — идентификатор окружения из
`environments_list`. Документ зовёт этот параметр `id` везде, кроме маршрута событий,
где он `environmentId`; каталог переименовывает его, поэтому все тулы принимают `id`.
Действия над контейнером — один тул `container_action`, аргумент
`action` выбирает start, stop, restart, kill, pause или unpause; проекты работают так же
через `project_action`.

## Выполнение команд в контейнере

В OpenAPI-документе Arcane операции exec нет. Терминал живёт на WebSocket-маршруте
`GET /api/agents/{id}/ws/containers/{containerId}/terminal?shell=/bin/sh&cols=&rows=`,
поэтому каталог его описать не может, и `container_exec` регистрируется вручную. Тул
выключен, пока оператор его не попросит: `--allow-exec` или `ARCANE_ALLOW_EXEC=true`,
а в `--read-only` он не регистрируется никогда. Он добавляет один тул сверх 445 из
каталога.

> **Этот тул выполняет произвольную команду внутри контейнера, с теми же правами, что
> у процесса, который там уже работает.** На нашей стороне ничего не квотируется и не
> сверяется со списком: строка уходит в шелл контейнера ровно как набрана. Включайте его
> только для того агента и того менеджера, где это и нужно, и считайте, что клиент
> с этим тулом держит шелл во всех контейнерах менеджера.

Что делает вызов: открывает одну TTY-сессию, пишет `command`, затем `exit`, читает,
пока сервер не закроет соединение, и закрывает его. Потока stdin нет — сессия
заканчивается вместе с командой и закрывается на любом пути, включая таймаут и ошибку.

| Аргумент | По умолчанию | Что делает |
|---|---|---|
| `id` | — | Идентификатор окружения (агента), как его отдаёт `environments_list` |
| `container` | — | Идентификатор или префикс имени контейнера |
| `command` | — | Строка для шелла; пустая отклоняется, предел — 4 КиБ |
| `timeout_sec` | `30` | `1`–`300`; по истечении сессия закрывается, частичный вывод возвращается |
| `instance` | — | Имя инстанса, как у остальных тулов |

Ещё два предела фиксированы: ответ обрезается на 64 КиБ с пометкой `[truncated at
65536 bytes]`, а кадр больше 1 МиБ завершает сессию.

Что в ответе есть и чего в нём нет:

- **Код выхода читается из строки-маркера.** Arcane статус не присылает: exec идёт с TTY,
  сокет закрывается по завершении шелла, а `ExecInspect` менеджер не выставляет. Поэтому
  после команды тул печатает в тот же шелл ещё одну строку — `printf '__mcp_exit:%d__\n'
  $?` — читает из неё число, вырезает из ответа и её эхо, и саму строку, и завершает ответ
  строкой `exit: N`. Если команда завершает шелл сама (`exit`, `exec`, убийство), маркер не
  выполнится: статуса в ответе нет, а в аудите стоит `exit=unavailable`.
- **Эхо TTY.** Сессия интерактивная, поэтому вывод повторяет команду и приглашение,
  сохраняет переводы строк `\r\n` и содержит управляющие последовательности терминала.
  Сервер отдаёт `stdout` и `stderr` слитно.
- **Отказы до запуска шелла** приходят строкой текста и затем аварийным закрытием; тогда
  в ответе есть `[session closed <code>: <reason>]`.

Каждый вызов пишет одну строку в стандартный поток ошибок сервера:
`container_exec agent=… container=… exit=<статус|unavailable> status=ok|timeout|closed <code>: <reason>|<текст ошибки>
duration=… command="…"`, команда обрезана до 200 символов.

## Запуск

```sh
make build-arcane                       # ./arcane-mcp
ARCANE_API_KEY=... ./arcane-mcp --url http://arcane:3552 --toolsets core,containers
# или образ из релиза: нужен -i, транспорт stdio
docker run -i --rm -e ARCANE_API_KEY \
  ghcr.io/akrhin/arcane-mcp:v0.4.3 --url http://arcane:3552
```

Файла конфигурации нет. Один процесс обслуживает один менеджер, заданный `--url`;
транспорт — stdio, HTTP-слушателя нет. Ключ приходит из `--api-key` и по умолчанию
равен ссылке `${ARCANE_API_KEY}`, поэтому незаданная переменная падает на старте, а
не отправляет пустой заголовок.

| Флаг | По умолчанию | Действие |
|---|---|---|
| `--url` | — | Базовый URL менеджера, например `http://arcane:3552`; обязателен |
| `--api-key` | `${ARCANE_API_KEY}` | Значение заголовка `X-API-Key` |
| `--name` | `arcane` | Имя инстанса в текстах ошибок |
| `--toolsets` | все | Имена наборов через запятую |
| `--read-only` | `false` | Регистрировать только тулы с `readOnlyHint: true` |
| `--exhaustive` | `false` | Регистрировать все операции включённых наборов |
| `--allow-exec` | `false` | Добавить `container_exec`, разовый шелл в контейнере; `ARCANE_ALLOW_EXEC=true` включает его тоже, а `--read-only` сильнее обоих |
| `--version` | — | Напечатать `arcane-mcp <version> (<commit>, <date>)` и выйти |

Запись в клиенте:

```json
{
  "mcpServers": {
    "arcane": {
      "command": "/usr/local/bin/arcane-mcp",
      "args": ["--url", "http://arcane:3552", "--toolsets", "core,containers,projects"],
      "env": { "ARCANE_API_KEY": "..." }
    }
  }
}
```

## Перегенерация каталога

Сконвертированный документ лежит в репозитории; вендорный JSON, из которого он получен,
— нет. Чтобы обновить, сохраните OpenAPI 3.1 документ менеджера как
`arcane-openapi.json` в корне репозитория и выполните:

```sh
make spec-arcane    # go run ./tools/specgen -in arcane-openapi.json -out api/arcane-3.1.yaml
make catalog        # go run ./tools/cataloggen, оба профиля
```

`specgen` конвертирует документ 3.1 детерминированно: ключи `$schema` выбрасываются,
массив `type` сворачивается в единственный не-`null` элемент, числа сохраняют целую
форму, а список `servers` заменяется на `/api`. Повторный прогон по тому же входу даёт
те же байты.

## Ограничения этого захода

- В OpenAPI-документе Arcane 3.0.1 операции exec нет: терминал — это WebSocket-маршрут,
  который каталог описать не может, поэтому `container_exec` написан руками и выключен
  по умолчанию (см. выше). Протокол не сообщает код выхода.
- Теги Stream (server-sent events), Uploads, Mobile Push, MFA, Passkeys и OIDC
  достижимы через свои наборы, все выключены по умолчанию (`events` кроме двух тулов
  по умолчанию). Церемония passkey или OIDC всё равно требует настоящего браузера:
  тулы открывают API, а не аутентификатор человека.
- Тулы `/auth/me/…` на API-ключ отвечают `401 unauthorized`: Arcane принимает там только
  пользовательскую сессию, так что `passkey_*` и `mfa_*` доходят до маршрута, но не до
  результата.
- Операции `HEAD` тела не отдают, поэтому `health_check_head` и `system_health_head`
  существуют для полноты, а не для работы.
- Образы контейнеров из релизного workflow по-прежнему содержат только
  `portainer-mcp`; бинарь Arcane едет в архивах.
- Клиент Arcane переиспользует HTTP-исполнитель Portainer с другим заголовком
  авторизации и другим префиксом ошибок. Транспорт у серверов общий, поэтому
  исправление в одном доходит до обоих.
