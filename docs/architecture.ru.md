# Архитектура

Четыре пакета и одно направление зависимостей: `cmd` связывает `config`, `catalog`,
`mcpserver` и `portainer`; `cmd` не импортирует никто.

| Путь | Содержимое |
|---|---|
| `cmd/portainer-mcp/` | Точка входа: флаги, загрузка каталога, загрузка конфигурации, транспорт |
| `internal/catalog/` | Типы каталога, разбор YAML, валидация, вшитый `catalog.yaml` |
| `internal/config/` | YAML-конфигурация, подстановка `${VAR}`, валидация по каталогу |
| `internal/mcpserver/` | Регистрация из каталога, обработчики тулов, выбор инстанса |
| `internal/portainer/` | HTTP-клиент к API Portainer |
| `internal/mcpserver/testdata/` | Golden-файл списка зарегистрированных тулов |
| `scripts/` | `docs-check.sh` (ворота документации), `smoke.sh` (живой прогон по stdio) |

## Каталог — это интерфейс

`internal/catalog/catalog.yaml` вшивается через `//go:embed` и разбирается при
старте. В нём имя, описание, аннотации, схема входа и схема выхода каждого тула.
`mcpserver` превращает запись каталога в `mcp.Tool` и регистрирует обработчик с этим
именем; собственных метаданных у обработчика нет.

Что из этого следует:

- Тул, которого нет в каталоге, зарегистрировать нельзя, а обработчик без записи в
  каталоге недостижим.
- Read-only — фильтр на регистрации, а не проверка во время вызова: `selectTools`
  выбрасывает каждый тул, у которого `readOnlyHint` не истинен, поэтому
  `tools/list` отброшенный тул не показывает.
- Golden-тест сравнивает зарегистрированный `tools/list` с
  `internal/mcpserver/testdata/tools_core.golden.json`, так что правка каталога,
  меняющая поверхность, валит набор тестов, пока golden-файл не перегенерируют.

Валидация идёт по вшитому документу на каждом старте, поэтому сломанный каталог
падает до открытия любого транспорта: неподдерживаемая `version`, набор без имени
или с повтором имени, повтор имени тула, тул без `readOnlyHint`, write-тул без
`destructiveHint`, `input` или `output` с `type`, отличным от `object`, и
зависимость от необъявленного набора.

## Старт

`main.run` выполняет шаги в этом порядке, и любой сбой завершает процесс строкой
`portainer-mcp: <ошибка>` в stderr с кодом 1:

1. Разбор `--config`, `--toolsets`, `--read-only`, `--exhaustive`.
2. Загрузка и валидация вшитого каталога.
3. Проверка списка `--toolsets` по каталогу — до чтения файла конфигурации.
4. Загрузка файла: декодирование с отказом на неизвестные поля, подстановка
   `${VAR}`, затем валидация инстансов, наборов и транспорта.
5. Сборка сервера: вычисление итогового списка наборов и флага read-only, отказ на
   `exhaustive`, проверка зависимостей, отказ на наборе без обработчиков.
6. Создание по одному `portainer.Client` на каждый настроенный инстанс.
7. Регистрация выбранных тулов, затем запуск транспорта.

Итоговые настройки: `--toolsets` заменяет `toolsets`, если непуст; `--read-only` и
`server.read_only` складываются по ИЛИ; `--exhaustive` и `server.exhaustive`
складываются по ИЛИ, и любого из них достаточно для отказа.

Отказ на регистрации не молчит. Если выборка осталась без тулов — например, всё
отфильтровал read-only, — `New` возвращает `no tools selected for toolsets ...`,
а не отдаёт пустой сервер.

## Поток запроса

```text
MCP-клиент
  → stdio или Streamable HTTP по /mcp
  → SDK вызывает CallTool для зарегистрированного имени
  → adapt: разбор аргументов в map[string]any
  → обработчик: выбор инстанса, вызов клиента Portainer
  → portainer.Client.get: GET по HTTP с X-API-KEY
  → adapt: маршалинг результата в текстовый контент и structuredContent
```

Ошибки устроены так:

- `adapt` никогда не возвращает протокольную ошибку на сбой API. Он превращает
  ошибку в результат с `isError: true` и текстом ошибки в контенте, так что упавший
  вызов Portainer для модели — отказ тула, а не сломанная сессия.
- Разбор аргументов строг на верхнем уровне: аргументы, не являющиеся JSON-объектом,
  дают результат `isError` с `arguments must be a JSON object: ...`. Типы
  проверяются в каждом обработчике — `environment_inspect` требует целочисленный
  `id` и отвечает `id is required` или `id must be an integer`.

Выбор инстанса живёт в слое обработчиков. Каждый тул принимает необязательную строку
`instance`; пустая или отсутствующая — первый настроенный инстанс, а неизвестное имя
даёт `unknown instance "x" (configured: ...)`.

## Клиент Portainer

`internal/portainer` — read-клиент, а не сгенерированный SDK. Он даёт по методу на
эндпоинт `core`, и все они — тонкие обёртки над `get`:

| Метод | Путь |
|---|---|
| `SystemVersion` | `/api/system/version` |
| `SystemStatus` | `/api/system/status` |
| `SystemInfo` | `/api/system/info` |
| `Settings` | `/api/settings` |
| `CurrentUser` | `/api/users/me` |
| `Endpoints` | `/api/endpoints` |
| `Endpoint(id)` | `/api/endpoints/{id}` |

`New` собирает HTTP-клиент: таймаут 120 секунд, `X-API-KEY` в каждом запросе,
`Accept: application/json` и TLS-конфигурацию, где `InsecureSkipVerify` — отрицание
`tls_verify`. Если задан `ca_file`, его PEM-сертификаты добавляются к системному
хранилищу; нечитаемый файл или файл без сертификатов — ошибка сборки клиента.

Ответы не из 2xx становятся `*APIError` со статусом и телом ответа до 4 КиБ. Его
`Error` различает три статуса, которые встречает оператор: 401 указывает на
API-ключ, 403 говорит, что ключ не может выполнить операцию, 404 сообщает об
отсутствующем ресурсе; остальное падает в
`portainer: <status> <status text>: <body>`.

Тулы `core` возвращают `json.RawMessage` там, где форма ответа — дело Portainer, и
урезанную структуру в `environment_list`, где числовые тип и статус переводятся в
имена.

## Транспорты

- **stdio** (по умолчанию): `srv.Run(ctx, &mcp.StdioTransport{})`. В stdout не идёт
  ничего, кроме протокольных сообщений; ошибки старта уходят в stderr.
- **Streamable HTTP**: `mcp.NewStreamableHTTPHandler` возвращает один и тот же сервер
  на каждый запрос, смонтированный по `/mcp` на свежем `http.ServeMux`. Слушатель
  открыт обычным HTTP — TLS забота фронтового прокси. Своего слоя аутентификации
  у него нет: кто дошёл до порта, пользуется настроенными API-ключами.

Ревизию протокола согласует SDK (`github.com/modelcontextprotocol/go-sdk` v1.8.0),
который говорит на `2026-07-28`; репозиторий свою ревизию не фиксирует.
Smoke-скрипт отправляет `2026-07-28` в запросе `initialize`.

## Чего в этапе 0 нет

- Обработчиков для `docker`, `swarm`, `k8s`, `helm`, `stacks`, `gitops`, `edge`,
  `admin`, `observability` и `raw`; включение любого — ошибка старта.
- Сгенерированного клиента и режима `--exhaustive`; это придёт с клиентом по OpenAPI
  на этапе 1.
- Повторов, ограничения частоты, кеша и журнала запросов в клиенте Portainer.
- Состояния на сессию: HTTP-обработчик обслуживает одно общее значение сервера, а
  всё, что относится к запросу, живёт в его контексте.
