# Архитектура

Шесть Go-пакетов и одно направление зависимостей: `cmd` связывает `catalog`,
`config`, `mcpserver` и `portainer`; `tools/cataloggen` — генератор времени сборки,
который импортирует типы каталога; `cmd` не импортирует никто. Спецификации API в
`api/` — вход генератора, а не скомпилированный код.

| Путь | Содержимое |
|---|---|
| `cmd/portainer-mcp/` | Точка входа: флаги, загрузка каталога, загрузка конфигурации, транспорт |
| `api/` | Два OpenAPI-документа плюс курируемые `toolsets.yaml` и `default-tools.yaml` |
| `tools/cataloggen/` | Генератор за `make catalog`; пишет `internal/catalog/generated.yaml` |
| `internal/catalog/` | Типы каталога, вшивание и слияние двух документов, валидация |
| `internal/config/` | YAML-конфигурация, подстановка `${VAR}`, валидация по каталогу |
| `internal/mcpserver/` | Регистрация из каталога, единственный обработчик тулов, выбор инстанса |
| `internal/portainer/` | HTTP-исполнитель, помощники ответа, клиент инстанса |
| `internal/mcpserver/testdata/` | Golden-файлы зарегистрированного `tools/list` |
| `scripts/` | `docs-check.sh` (ворота документации), `smoke.sh` (живой прогон по stdio) |

## Каталог — это интерфейс

Каталог состоит из двух вшитых документов. `internal/catalog/catalog.yaml`
курируется руками и хранит только имена одиннадцати наборов, описания и рёбра
`depends_on`. `internal/catalog/generated.yaml` хранит каждый тул — имя, описание,
аннотации, схему входа, необязательную схему выхода и HTTP-операцию. `catalog.go`
вшивает оба через `//go:embed`, а `Merge` (`internal/catalog/catalog.go:98`)
прикрепляет сгенерированные тулы к курируемым наборам. Слияние отвергает набор,
который есть только в одном документе, несовпадение версий и список тулов внутри
`catalog.yaml`.

Сгенерированный документ руками не пишут. `make catalog`
(`go run ./tools/cataloggen`) читает спецификации Portainer 2.45 и Docker Engine
1.57 в `api/`, карту «тег → набор» в `api/toolsets.yaml` и список по умолчанию в
`api/default-tools.yaml`, затем пишет файл. Вывод детерминирован, а
`TestBuildMatchesCommittedFile` падает, когда закоммиченный файл расходится со свежим
прогоном.

Что из этого следует:

- Тул, которого нет в сгенерированном каталоге, зарегистрировать нельзя.
- Read-only — фильтр на регистрации, а не проверка во время вызова: `selectTools`
  (`internal/mcpserver/server.go:58`) выбрасывает каждый тул, у которого
  `readOnlyHint` не истинен, а без `--exhaustive` — ещё и каждый тул без
  `default: true`.
- Golden-тест сравнивает `tools/list` для `core` и `docker` с
  `internal/mcpserver/testdata/tools_core_docker.golden.json` (20 тулов по
  умолчанию), так что правка каталога, меняющая поверхность, валит набор, пока
  файл не перегенерируют.

Валидация идёт по слитому каталогу на каждом старте, до открытия любого транспорта:
неподдерживаемая `version`, набор без имени или с повтором имени, повтор имени тула,
тул без `readOnlyHint`, write-тул без `destructiveHint` или `idempotentHint`,
`input` с типом не `object`, `output` с типом ни `object`, ни `array`, стриминговый
параметр, которого нет среди свойств входа, путь операции без ведущего `/` и
зависимость от необъявленного набора.

## Старт

`main.run` выполняет шаги в этом порядке, и любой сбой завершает процесс строкой
`portainer-mcp: <ошибка>` в stderr с кодом 1:

1. Разбор `--config`, `--toolsets`, `--read-only`, `--exhaustive` и `--version`.
   `--version` печатает `portainer-mcp <version> (<commit>, <date>)` и выходит до
   чтения каталога и конфигурации.
2. Загрузка и валидация слитого каталога.
3. Проверка списка `--toolsets` по каталогу — до чтения файла конфигурации.
4. Загрузка файла: декодирование с отказом на неизвестные поля, подстановка
   `${VAR}`, затем валидация инстансов, наборов и транспорта.
5. Сборка сервера: вычисление итогового списка наборов, флагов read-only и
   exhaustive, проверка зависимостей, создание клиента на каждый инстанс, затем
   регистрация выбранных тулов.
6. Запуск транспорта.

Итоговые настройки: `--toolsets` заменяет `toolsets`, если непуст; `--read-only` и
`server.read_only` складываются по ИЛИ; `--exhaustive` и `server.exhaustive`
складываются по ИЛИ.

Отказ на регистрации не молчит. Если выборка осталась без тулов — например, всё
отфильтровал read-only, — `New` возвращает `no tools selected for toolsets ...`, а не
отдаёт пустой сервер.

## Поток запроса

```text
MCP-клиент
  → stdio или Streamable HTTP по /mcp
  → SDK вызывает CallTool для зарегистрированного имени
  → adapt: разбор аргументов в map[string]any
  → обработчик: выбор инстанса, сборка запроса из записи каталога
  → portainer.Client.Do: HTTP с X-API-KEY
  → apiResult: вырезание managedFields, формирование ответа, structuredContent
```

Обработчик (`internal/mcpserver/tools.go:20`) превращает одну запись каталога в
запрос: параметры пути экранируются и подставляются, каждое оставшееся свойство
входа становится параметром запроса (массивы — повторёнными ключами или одним
значением через запятую, где так сказано в каталоге), а свойство тела уходит JSON-ом.
Сырые тулы берут метод и путь из аргументов и дописывают путь к своей базе, отвергая
путь без ведущего `/` или с `..`.

Ошибки устроены так:

- `adapt` никогда не возвращает протокольную ошибку на сбой API. Он превращает
  ошибку в результат с `isError: true` и текстом ошибки в контенте, так что упавший
  вызов Portainer для модели — отказ тула, а не сломанная сессия.
- Разбор аргументов строг на верхнем уровне: аргументы, не являющиеся JSON-объектом,
  дают результат `isError` с `arguments must be a JSON object: ...`. Отсутствующий
  параметр пути даёт `missing path parameter: ...`; отсутствующее обязательное тело
  даёт `<name> is required`.

Выбор инстанса живёт в слое обработчиков. Каждый тул принимает необязательную строку
`instance`; пустая или отсутствующая — первый настроенный инстанс, а неизвестное имя
даёт `unknown instance "x" (configured: ...)`.

## Формирование ответа

`internal/portainer/exec.go` и `apiResult` решают, что дойдёт до модели:

- **Отказ на стриминге.** Четыре тула несут `follow` (`container_logs`,
  `service_logs`, `task_logs`, `kubernetes_pod_logs`), три стримят по пути
  (`system_events`, `container_attach`, `exec_start`). Вызов, который висел бы,
  отвергается до отправки запроса, а сообщение называет предел, который надо
  задать: `follow=false` или `until`.
- **Метаданные Kubernetes.** 116 тулов, чей путь операции содержит `/kubernetes/`,
  несут `strip_managed_fields: true`; `metadata.managedFields` вырезается на любой
  глубине до сериализации ответа.
- **Предел размера.** Тело ответа обрезается на 1 МиБ (`MaxResponse` в
  `internal/portainer/exec.go:17`). Обрезанный JSON-массив становится страницей:
  первые 50 элементов плюс `_truncated`, `_total` и `_hint`. Обрезанный не-массив
  сохраняет маркер `…[truncated at N bytes: ...]`.
- **Structured content.** Полный JSON-ответ возвращается и текстом, и в
  `structuredContent`; у 237 тулов объявлена схема выхода, которая становится
  `outputSchema` тула.

## Клиент Portainer

`internal/portainer` — HTTP-исполнитель, а не сгенерированный SDK. Каждый тул идёт
через `(*Client).Do` (`internal/portainer/exec.go:31`), который отправляет метод,
путь, query и тело с `X-API-KEY` и `Accept: application/json` и читает не больше
`MaxResponse + 1` байт.

`New` собирает HTTP-клиент: таймаут 120 секунд и TLS-конфигурацию, где
`InsecureSkipVerify` — отрицание `tls_verify`. Если задан `ca_file`, его
PEM-сертификаты добавляются к системному хранилищу; нечитаемый файл или файл без
сертификатов — ошибка сборки клиента.

Ответы не из 2xx становятся `*APIError` со статусом и телом ответа до 4 КиБ. Его
`Error` различает три статуса, которые встречает оператор: 401 указывает на
API-ключ, 403 говорит, что ключ не может выполнить операцию, 404 сообщает об
отсутствующем ресурсе; остальное падает в
`portainer: <status> <status text>: <body>`.

## Транспорты

- **stdio** (по умолчанию): `srv.Run(ctx, &mcp.StdioTransport{})`. В stdout не идёт
  ничего, кроме протокольных сообщений; ошибки старта уходят в stderr.
- **Streamable HTTP**: `mcp.NewStreamableHTTPHandler` возвращает один и тот же сервер
  на каждый запрос, смонтированный по `/mcp` на свежем `http.ServeMux`. Слушатель
  открыт обычным HTTP — TLS забота фронтового прокси. Своего слоя аутентификации
  у него нет: кто дошёл до порта, пользуется настроенными API-ключами.

Ревизию протокола согласует SDK (`github.com/modelcontextprotocol/go-sdk` v1.8.0),
который говорит на `2026-07-28`; репозиторий свою ревизию не фиксирует.
Smoke-скрипт отправляет `2026-07-28` в запросе `initialize`.

## Чего сервер не делает

- Ни повторов, ни ограничения частоты, ни кеша, ни журнала запросов перед Portainer.
- Ни переноса websocket: `/containers/{id}/attach/ws` исключён через `skip_paths` в
  `api/toolsets.yaml`, потому что вызов тула «запрос-ответ» такой поток не удержит.
- Ни состояния на сессию: HTTP-обработчик обслуживает одно общее значение сервера, а
  всё, что относится к запросу, живёт в его контексте.
